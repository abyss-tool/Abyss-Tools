## 1. 目标与范围

定义 19 个仓库的角色、数据流向与单一事实源；开发仓不存签名材料、发布仓不存源码。

## 2. 现状锚点（克隆研究实测）

- `Abyss-Tools/README.md`
- `Abyss-Tools/core/common/.../AbyssChannels.kt`
- `Abyss-Tools-Release/version.json`
- `Abyss-Plugins/plugins.json`

> 研究口径：2026-11-21 对 `github.com/abyss-tool` 组织下 19 个公开仓库（主仓 / 发布仓 / 插件中心 / 13 归档插件仓 / 3 引擎级插件仓）全量拉取，共 511 个文件；主仓 296 个文件、约 22 个 feature 模块。

## 3. 功能需求

| 编号 | 需求描述（原子、可验证） |
|---|---|
| FR-001 | `Abyss-Tools` 为唯一源码与 CI 门禁所在；版本号只住在 AppInfo.kt。 |
| FR-002 | `Abyss-Tools-Release` 只持有 version.json / patches.json / changelog.json 与 APK 资产。 |
| FR-003 | `Abyss-Plugins/plugins.json` 是插件中心的唯一运行时数据源，由 sync-index.yml 聚合。 |
| FR-004 | 13 个归档插件仓保持只读归档，禁止再发布补丁但保留历史 manifest 供审计。 |
| FR-005 | 3 个引擎级插件仓各自持有 plugin.json / patches/index.json / plugin-ci.yml / patch-release.yml。 |
| FR-006 | 双仓发布：tag 或 auto-release 触发后，APK 资产同时留存主仓与发布仓。 |

> 纪律：每条 FR 必须至少被一条 AC 或一个自动化用例覆盖；下表 AC 为关键验收条件，完整覆盖关系由 `QA-008 需求追溯矩阵` 与 spec-lint 登记校验。需求变更需同步更新本文件与对应的测试夹具（`src/test/resources` 为通道契约镜像）。

## 4. 契约与接口

```
Abyss-Tools（源码 + CI）
   │ tag v* / push main（auto-release.yml）
   ▼
Abyss-Tools-Release（Release + APK + 三件套清单） ──→ 客户端 UpdateChecker
Abyss-Plugins（plugins.json） ──→ 客户端 PluginRepository
abyss-plugin-{app-builder,virus-guard,virtual-machine} ──→ 独立补丁通道
```

## 5. 失败语义与边界

- 归档仓 manifest 中的 `Ultra-Guru/...` 旧组织字段属历史漂移，不得被运行时索引采纳。
- ChannelPolicy 只接受 `abyss-tool/abyss-plugin-*` 形态的 repo。

## 6. 验收标准

| 编号 | 验收条件 |
|---|---|
| AC-001 | 19 仓角色清单与 GitHub API 返回的 default_branch / archived 状态一致。 |
| AC-002 | version.json 的 versionName 与 AppInfo.VERSION_NAME 严格相等。 |

> 验收方法：纯 JVM 单测（`./gradlew test`）/ CI 门禁脚本 / 真机回归清单（Android 15 与 16 各一台）/ 通道清单校验，按单元性质择一或组合。

## 7. 依赖与风险

**风险**
