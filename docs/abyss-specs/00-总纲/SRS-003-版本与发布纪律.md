## 1. 目标与范围

版本号单一事实源、versionCode 单调门禁、发布要点来源、跳过语义与写后自检回读。

## 2. 现状锚点（克隆研究实测）

- `Abyss-Tools/core/common/src/main/kotlin/com/abyss/tools/core/common/AppInfo.kt`
- `Abyss-Tools/app/build.gradle.kts`
- `Abyss-Tools/.github/workflows/auto-release.yml`
- `Abyss-Tools/tools/publish_release.py`

> 研究口径：2026-11-21 对 `github.com/abyss-tool` 组织下 19 个公开仓库（主仓 / 发布仓 / 插件中心 / 13 归档插件仓 / 3 引擎级插件仓）全量拉取，共 511 个文件；主仓 296 个文件、约 22 个 feature 模块。

## 3. 功能需求

| 编号 | 需求描述（原子、可验证） |
|---|---|
| FR-001 | 版本号字面量只允许出现在 AppInfo.kt；build.gradle.kts 经正则推导。 |
| FR-002 | 版本比较统一使用 SemVer，禁止手写 split('.') 比较。 |
| FR-003 | versionCode 必须严格大于通道现值，防误发旧版本把 latest 拉回。 |
| FR-004 | commit message 含 `[skip release]` 时本次不发布；`[skip ci]` 防自触发。 |
| FR-005 | 发布要点取自 docs/release-notes/v<版本>.md 或 dispatch 输入。 |
| FR-006 | publish_release.py 写后必须自检回读三件套清单一致性。 |

> 纪律：每条 FR 必须至少被一条 AC 或一个自动化用例覆盖；下表 AC 为关键验收条件，完整覆盖关系由 `QA-008 需求追溯矩阵` 与 spec-lint 登记校验。需求变更需同步更新本文件与对应的测试夹具（`src/test/resources` 为通道契约镜像）。

## 4. 契约与接口

```kotlin
object AppInfo {
    const val VERSION_NAME: String = "0.9.5"
    const val VERSION_CODE: Int = 28
}
```
`auto-release.yml`：AppInfo 未发布的新 VERSION_NAME 原样采用；已发布过则 patch 自动递增。

## 5. 失败语义与边界

- 坏数据 / 非法版本 / 路径穿越 / 签名不符一律 fail-closed 拒绝并给人话错误，不猜测、不静默降级。
- 远端数据统一走 `UiState`（Loading / Error / Data），加载中禁止展示假数据。

## 6. 验收标准

| 编号 | 验收条件 |
|---|---|
| AC-001 | 修改 AppInfo 后 CI 的 validate_manifests.py 通过。 |
| AC-002 | version.json 与 changelog.json 的 versionName/versionCode 一致。 |

> 验收方法：纯 JVM 单测（`./gradlew test`）/ CI 门禁脚本 / 真机回归清单（Android 15 与 16 各一台）/ 通道清单校验，按单元性质择一或组合。
