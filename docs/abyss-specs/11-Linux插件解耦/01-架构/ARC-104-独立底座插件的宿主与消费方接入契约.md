## 1. 先把「能用」拆成三个不同的问题

| # | 问题 | 答案 | 机制 |
| --- | --- | --- | --- |
| ① | **其他插件**能用独立底座吗 | ✅ 能 | `depends` → `DependencyResolver` → `CapabilityBinder` 四重校验 → `SessionGrant` → 宿主 `bindService` → 受限 `ILinuxSession` 代理 |
| ② | **主软件（宿主）**能管理和绑定底座吗 | ✅ 能，本来就是这么设计的 | `PluginBroker` 就在主壳进程里，宿主→提供方是唯一合法绑定方向 |
| ③ | **主软件自己的功能模块**能消费 Linux 会话吗（跑命令 / 开 PTY） | ✅ 能，**但需补一条内部通道** | 主壳不是「索引里的消费方插件」，走不了 `getCapability` 白名单；需 `getInternalSession()`，见 §4 |

> 容易混的是 ② 和 ③：② 是「宿主管理插件」，天然成立；③ 是「宿主自己也当消费方」，现有 `CapabilityBinder.isConsumerPlugin()` 会把宿主自己拒掉（`E_DIRECT_BIND_DENIED`），所以必须显式补一条通道。这是本轮唯一需要新增的机制，其余全部复用已落地代码。

## 2. 证据：代码里已经铺好的链路

### 2.1 底座侧（独立 APK 确实对外暴露了服务）

`abyss-plugin-linux/app/src/main/AndroidManifest.xml`：

```xml
<service
    android:name=".LinuxRuntimeService"
    android:exported="true">
    <intent-filter>
        <action android:name="com.abyss.tools.plugin.action.LINUX_RUNTIME" />
    </intent-filter>
    <meta-data android:name="com.abyss.tools.plugin.HOST_ENTRY"
               android:value="com.abyss.plugin.linux.LinuxRuntimeService" />
</service>
```

`LinuxRuntimeService.kt` 注释明确写：「exported 为跨 APK 绑定所必需；宿主 PluginBroker 经 `HostContractActions.ACTION_LINUX_RUNTIME` 发现」。`HostContractActions.kt` 里 `HOST_API_VERSION = 2`、动作串 `com.abyss.tools.plugin.action.LINUX_RUNTIME` 与宿主 `PluginContract` 逐字对齐，CI 以 manifest + 集成测试锚定。

**没有 `android:permission` 声明** —— 所以安全不靠 Manifest 权限，靠 `onBind` 里的调用方校验 + `SessionGrant` 五元组（见 §6 待补门禁）。

### 2.2 宿主侧（主壳里已经有完整的绑定与授权实现）

`Abyss-Tools/core/plugin/` 下已落地：

| 文件 | 已实现职责 |
| --- | --- |
| `DependencyResolver.kt` | 解析 `depends[]`、SemVer 区间、DAG 环检测、拓扑安装序；注释直引「ARC-102 §3 —— HOST_API v2 的核心新增职责」 |
| `CapabilityBinder.kt` | `getCapability()` 四重校验：包名白名单 / 签名集 == 发布者指纹 / `depends` 匹配 / `minHost`；任一失败返回人话错误码，不给半可用 Binder |
| `SessionGrantIssuer.kt` | 五元组（callerPackage / signerSha256 / capability / sessionId / nonce）+ TTL ≤300s + 宿主签名含代际 + 一次性 nonce |
| `ChannelPolicy.kt` | 索引条目运行时白名单：id 形态、repo 归属、URL 域、sha256 必填，fail-closed |
| `ToolCatalog.kt:110` | 已有 `id="linux-runtime"` / `pluginId="abyss-plugin-linux"` 的 PLUGIN 条目 |
| `PluginBrokerTest.kt` / `ToolCatalogPluginBindingTest.kt` | 已有集成/契约测试 |

`ARC-102 §4` 时序图逐笔画出了完整链路：消费方 ① `getCapability` → 宿主 ② 校验调用方 → ③ `PackageManager` 查询 `ACTION_LINUX_RUNTIME` 并 `bindService` → ④ 签发 `SessionGrant` → 消费方 ⑤ `openSession(spec, grant)` → 插件 ⑥ 校验 grant → ⑦ `exec / fileIn / close` 全带 sessionId + grant。

### 2.3 消费方侧（已经有人在用这套契约）

`abyss-plugin-app-builder/plugin.json` 现状：

```json
{
  "id": "abyss-plugin-app-builder",
  "version": "0.2.0",
  "minHost": 2,
  "depends": [
    {
      "pluginId": "abyss-plugin-linux",
      "capability": "linux-runtime-v1",
      "versionRange": ">=0.2.0 <1.0.0",
      "optional": false
    }
  ]

```

`shizuku` 字段已删除（不再单独申请授权）。`Abyss-Plugins/plugins.json` hubVersion 已是 0.4.0，索引里 `abyss-plugin-linux` 的 `provides` 与 app-builder 的 `depends` 对得上。

### 2.4 跨进程数据真的传得动（不是纸上 AIDL）

| 数据 | 机制 | 为何可用 |
| --- | --- | --- |
| 命令输出流 | `IOutputSink` 是 `oneway` AIDL，`onChunk(byte[] chunk, boolean isError)` 分片回传 + `onResult` 终局 | 绕开 Binder 事务 1MB 硬上限；单流 1MB 累计上限、truncated 如实回传 |
| 文件写入 / 读取 | `ParcelFileDescriptor` 作为 AIDL 参数与返回值 | fd 跨进程传递是 Binder 原生能力，不走大事务 |
| PTY | `openPty(cols, rows, grant)` 返回 `PtyHandleData` | 句柄化，不把终端流塞进 Binder |
| 进程死亡 | 宿主与插件双向 `DeathRecipient` | 任一方死亡 → 会话 CLOSED、撤销 grant、UI 转 Error（N-PLG-002 FR-004） |
| 命令注入面 | `exec(ExecCommandData cmd)` 是 **argv 数组**，禁止 shell 字符串拼接 | 从根上消除注入（SEC-003） |

## 3. 三类调用方的完整接入路径

```
                          ┌──────────────────── 主壳进程（宿主）────────────────────┐
                          │  PluginBroker / DependencyResolver / CapabilityBinder   │
                          │  SessionGrantIssuer / ChannelPolicy                     │
                          │                                                        │
   ┌──────────────┐       │  ┌──────────────────────────────────────────────────┐  │
   │ 内置终端 /   │ ③内部 │  │ getInternalSession()  ★本轮新增                 │  │
   │ 脚本实验室 / │──────►│  │  caller = 宿主包名，internal grant，跳过白名单   │  │
   │ 未来主壳功能 │       │  │  但仍做签名校验 + 能力收敛 + 全程审计           │  │
   └──────────────┘       │  └──────────────────┬───────────────────────────────┘  │
                          │                     │                                 │
   ┌──────────────┐  ①   │  getCapability() ────┤                                 │
   │ app-builder  │──────►│  四重校验 ───────────┤                                 │
   │ phone-server │       │                     │  ② bindService                  │
   │ virus-guard* │       │                     ▼                                 │
   └──────────────┘       └─────────────────────┼─────────────────────────────────┘
          ▲                                     │  ACTION_LINUX_RUNTIME
          │ ⑤ 受限 ILinuxSession 代理           ▼
          │                    ┌──────────────────────────────────────┐
          └────────────────────┤  独立 APK：abyss-plugin-linux        │
                               │  LinuxRuntimeService (exported=true)  │
                               │  ILinuxRuntime → openSession()        │
                               │  PRoot / UML / QEMU + Shizuku 自有授权 │
                               └──────────────────────────────────────┘
```

\* `virus-guard` 只有在 `plugin.json` 声明 `depends` 后才能拿到能力；未声明即 `E_DIRECT_BIND_DENIED`。这是**能力按声明授予**，不是限制。

| 调用方 | 入口 | 校验 | 拿到的东西 | 需要改代码吗 |
| --- | --- | --- | --- | --- |
| 其他插件（app-builder / phone-server） | `IAbyssPluginHost.getCapability("linux-runtime-v1")` | 四重 + `depends` 解析 + grant | 受限 `ILinuxSession` 代理 | **不用**，v1.0 已落地；phone-server 只需照抄 manifest 声明 |
| 主壳内部模块 | `getInternalSession()` ★ | 签名 + 能力收敛 + 审计 | 同一个受限 `ILinuxSession` 代理 | **要，本轮新增**（见 §4） |
| 宿主管理/发现 | `PackageManager` 查询 action + `bindService` | 调用方即宿主自己 | `ILinuxRuntime` binder | 不用，已实现 |
| 第三方 App 直连 | — | `onBind` 校验失败 → null | 无 | **要补**（见 §6 G-1） |

## 4. ★ 宿主自消费通道（本轮唯一新增机制）

### 4.1 为什么必须补

`CapabilityBinder.kt` 的 `CallerTrust.isConsumerPlugin(packageName)` 语义是「在索引中声明 `depends` 的消费方插件」。主壳包名（如 `com.abyss.tools`）**不在插件索引里**，因此若主壳内部模块直接调 `getCapability()`，会命中：

```kotlin
if (!trust.isConsumerPlugin(caller.packageName)) {
    return denied("E_DIRECT_BIND_DENIED", "请通过插件中心启动…")
}
```

### 4.2 设计

| 项 | 规定 |
| --- | --- |
| 新接口 | `PluginBroker.getInternalSession(spec, requesterId)`，仅主壳进程内可调用（Kotlin `internal` / 非 AIDL 暴露） |
| 身份 | `callerPackage = 宿主包名`、`callerSignerSha256 = 宿主自身签名`；**不经过 `isConsumerPlugin` 白名单** |
| grant | `SessionGrantIssuer.issue()` 照常签发，但标记 `grantScope = INTERNAL`（新增可选字段），TTL 收紧到 ≤60s，nonce 一次性不变 |
| 仍要做的校验 | 宿主签名自校验、请求能力 ∈ 内置能力矩阵 ∩ 底座 `provides`、`minHost`、底座已安装且版本达标、`ChannelPolicy` |
| 仍要做的纪律 | 能力可收紧不可放宽、每次 openSession 新 nonce、grant 不持久化、DeathRecipient、输出 1MB 上限 |
| 审计 | 内部会话单独记 `requesterId`（如 `internal:terminal` / `internal:script-lab`），与插件会话分账 |
| 降级 | 底座插件未安装 / 未授权 / 资产未就绪 → `E_RUNTIME_UNAVAILABLE` + 一键引导安装，**绝不谎报可用** |
| 既有功能不受影响 | v0.8.0 已内置的「内置终端（Shizuku Shell）」「脚本实验室（Python）」继续走原路径；这条通道只服务**新增的、明确要 Linux 底座的主壳功能** |

> 一句话：主壳既是裁判又是选手时，不能让裁判拿选手的报名表拦自己；但也不能给自己发免检通行证 —— 签名、能力、审计一样不少。

## 5. B 方案下 Shizuku 授权为什么反而更干净

| 主体 | Shizuku 授权 | 说明 |
| --- | --- | --- |
| `abyss-plugin-linux`（独立 APK） | **1 次，自己持有** | PRoot / UML / QEMU 进程由它经 uid 2000 上下文拉起；`plugin.json` 已写 `shizuku.ownAuth=true`，理由即「per-app 授权不继承，本插件为全生态唯一持有方」 |
| 主壳 | 不因 Linux 底座而申请 | 通过 Binder 间接消费；主壳若有自己的 Shizuku 功能（内置终端）属于另一回事，与底座无关 |
| app-builder / phone-server / virus-guard | **0 次** | app-builder 已删 `shizuku` 字段；服务器插件 `ownAuth=false` |

per-app 授权不继承在这里是**优点**：权限边界收敛在底座一个进程里，不会出现「主壳和插件各申请一次、用户点两遍」的混乱。

## 6. 诚实边界：现在「架构能」≠「装上就能跑」

以下是 2026-11-27 实测状态，必须写进规格，不能含糊：

| # | 现状 | 影响 | 归属门禁 |
| --- | --- | --- | --- |
| **G-1** | `LinuxRuntimeService.onBind()` 目前**只校验 action**，源码注释写「grant 五元组校验随 M1 落地」 | `exported=true` 意味着任意 App 都能尝试绑定；B 方案下必须把「调用方签名 == 宿主签名 + grant 有效」做成 `onBind` 硬门禁，否则返回 null | **M0 阻塞项** |
| **G-2** | `LinuxRuntimeBinder.openSession()` 当前**一律抛 `E_RUNTIME_UNAVAILABLE`**；`runtimeSnapshot` 如实标注 `assetsReady=false` / `shizukuState=NOT_INSTALLED` | 会话、资产管线、域实现尚未接入；契约与时序成立但功能未通 | M1（T-012/T-013），按 `LIN-001/002/006` 落地 |
| **G-3** | 三个插件仓 `apk` 全为 `null`、无 Release 资产、`assets/index.json` 为空清单、全仓 0 个二进制资产 | 用户目前**装不到**底座插件 | 首次功能版本发布 |
| **G-4** | 底座插件是**可选安装**的独立 APK | 未安装时，所有依赖能力不可用；主壳必须 fail-closed 引导，不能显示「Linux 可用」 | `SRS-106 §5` 降级链 |
| **G-5** | 插件是独立进程 | 被系统回收 / 用户强停 / 升级覆盖 → 需 `DeathRecipient` 重连、重新签发 grant | `ARC-102` 已设计，需集成测试 |
| **G-6** | `ILinuxRuntime` / `ILinuxSession` 的 AIDL 全量方法已是 Parcelable + PFD + oneway callback | 跨进程能力本身没有技术阻塞 | 无需改动 |

> 所以对用户问题的精确回答是：**「能用」在架构、契约、代码骨架三层都成立，且已有现成实现承接；但当前仓库处于 M0 骨架期，真正跑起来要等 M1 会话实现 + 首个插件 APK 发布。** 不是「理论上可以」，也不是「现在就能点开用」。

## 7. M0 门禁清单（B 方案落地前必须闭环）

| 编号 | 门禁 | 验收 |
| --- | --- | --- |
| AC-001 | `onBind` 服务端校验：非宿主签名 → null；无 grant → null；非法 action → null | 第三方伪造 APK 绑定被拒，宿主绑定成功 |
| AC-002 | `getInternalSession()` 契约测试：主壳内部模块拿到受限会话，签名不符 / 能力越权 / 底座未装 三种情况均返回人话错误 | 单测 + 真机 |
| AC-003 | 消费方插件集成测试：app-builder 声明 depends → 宿主绑定 → grant → `ILinuxSession` 代理 → 越权项被拒 | `PluginBrokerTest` 扩展 |
| AC-004 | `DeathRecipient` 双端：强杀底座进程后，会话标记 CLOSED、grant 撤销、UI 转 Error 且可一键重连 | 真机 |
| AC-005 | 底座未安装时，主壳所有依赖入口显示「需安装 Linux 运行环境」+ 一键跳转，不出现半可用状态 | 真机 |

| AC-007 | 13 个 AIDL 方法签名 diff 为空（本轮不加新 AIDL 方法） | CI |
