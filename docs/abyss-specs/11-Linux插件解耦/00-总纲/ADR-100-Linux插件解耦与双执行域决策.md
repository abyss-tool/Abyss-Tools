# ADR-100 · Linux 底座独立为插件、双执行域统一会话

> 深渊工具 Abyss Tools · 架构决策记录
> 状态：**提议 · 待接受** ｜ 优先级：**P0** ｜ 里程碑：**M0** ｜ 编制日期：**2026-11-22**

| 项 | 值 |
| --- | --- |
| 规格编号 | `ADR-100` |
| 当前状态 | 提议 · 待接受 |
| 优先级 / 里程碑 | P0 / M0 |
| 关联 | 修订 `ADR-001`（补充例外）、承接 `HUB-011` / `HUB-013` / `N-APP-002` / `N-VM-001` |
| 决策影响 | 需主壳发版一次（HOST_API v2 + PluginBroker）；新增 1 仓、归档 1 仓 |

## 1. 背景

现状设计中，应用构建器自带「Alpine + PRoot」底座并单独申请 Shizuku 授权；虚拟机插件另起一套 QEMU + 镜像 + Shizuku 授权。两者都是骨架（无实现），但已能在架构上看出三处结构性问题：

1. **引擎重复**：一个 PRoot 底座、一个 QEMU 引擎、两套镜像/资产管线、两套前台服务、两次 per-app 授权；
2. **复用受限**：终端、脚本实验室、未来任何需要 Linux 的能力都得再复制一份底座；
3. **职责混杂**：构建器既要管编译路径，又要管 rootfs 解压、ptrace 探测、ROM 兼容降级，违反单一职责。

## 2. 决策

| 编号 | 决策 |
| --- | --- |
| D-1 | 新建 `abyss-plugin-linux`，作为**唯一**持有 Linux 运行环境与 Shizuku 授权的引擎级插件。 |
| D-2 | 插件提供两个执行域 `PROOT_USERLAND` / `QEMU_VM`，统一为 `RuntimeSession` 抽象与 `linux-runtime-v1` 能力。 |
| D-3 | 应用构建器改为瘦客户端，通过 `depends` 声明依赖，经宿主 `PluginBroker` 拿到受限 `ILinuxSession` 代理。 |
| D-4 | `abyss-plugin-virtual-machine` 归档，QEMU 能力收编；N-VM-* 与 DC-012 由 LIN-002 / DC-102 承接。 |
| D-5 | `HOST_API_VERSION` 1 → 2，新增依赖解析与能力绑定；v1 插件保留兼容期，v2 插件在 v1 宿主 fail-closed。 |
| D-6 | 新增 `abyss-asset-v1` 大资产通道，与 `abyss-patch-v1` 严格分离（沿用 ADR-011）。 |

## 3. 备选方案与否决理由

| 方案 | 描述 | 否决理由 |
| --- | --- | --- |
| A. 维持原设计 | 底座留在构建器，VM 独立 | 引擎重复、两次授权、无复用；骨架期不改，实现后拆分成本翻倍 |
| B. 底座内置主壳 | PRoot / QEMU 进 `Abyss-Tools` feature 模块 | 违反 ADR-001 三分法（自带完整引擎才插件化）；主壳变重且数 GB 资产无法随主壳发布 |
| C. 插件间直连 | 构建器直接 bind 导出 service，宿主不介入 | 无同签名校验、无依赖解析、无令牌；任意应用可冒充调用方，SEC-001/003 风险 |
| D. 只做 PRoot 域 | 不引入 QEMU，把 Alpine 抽出来即可 | 不满足「整个 Linux」字面；ptrace 被 ROM 拦截时无第二执行域可降级 |
| E. 只做 QEMU 域 | 全部构建跑完整 VM | TCG 仿真下 Gradle 构建耗时不可接受；冷启动分钟级；数 GB 镜像门槛过高 |
| F. Linux 插件做成数据插件 | 只下发 manifest + rootfs 数据 | rootfs / 镜像需独立进程与原生库，且 Shizuku 授权 per-app 要求独立 APK |

## 4. 后果

**正面**
- Shizuku 授权 2 次 → 1 次；底座 / 镜像 / 降级链只实现一次。
- 构建器代码量显著下降，三条路径可独立演进；新能力可复用 `linux-runtime-v1`。
- 资产与代码解耦：rootfs / 镜像可不发插件版而独立滚动。

**负面 / 成本**
- 主壳需发版一次，引入 PluginBroker、AIDL 接口与 HOST_API v2；跨进程调用带来序列化与死亡回调复杂度。
- 用户需装 3 个 APK（宿主 + Linux 插件 + 构建器），安装序与依赖引导必须做扎实。
- 插件间新增一条信任链：令牌签发、过期、撤销、DeathRecipient 都要测试。
- 双执行域意味着两套能力探测与性能基线，QA 成本上升。

**中性**
- `plugins.json` 由 3 条变 3 条（VM 换成 Linux），但字段变多、hubVersion 升级。

## 5. 回滚路径

| 触发条件 | 回滚动作 |
| --- | --- |
| HOST_API v2 主壳发版受阻 | 保留 v2 契约代码但默认关闭；Linux 插件与构建器降级为「同仓双模块」临时形态，仍各自独立 APK |
| 跨插件 Binder 在目标 ROM 上稳定性不达标 | 退回「宿主代理执行」模式：构建器把命令交给宿主，宿主转发 Linux 插件，性能略降但链路不变 |
| QEMU 域性能 / 存储不可接受 | 按 A-1 裁剪为仅 PRoot 域，LIN-002 与 M3 挂起，VM 仓暂缓归档 |
| 依赖解析引发安装失败率上升 | 允许 `depends.optional=true` 的过渡期（仅展示警告），但 M2 后必须收口为 fail-closed |

## 6. 纪律约束（不可协商）

- `HOST_API_VERSION` 只增不减；`minHost=2` 插件在 v1 宿主必须拒绝加载并提示升级（PLG-001 FR-001）。
- 同签名信任门 + 发布者指纹硬校验 + CI `apksigner` 实测，三层信任链不变（SEC-001）。
- Shizuku 不是 root，不得暗示绕过厂商安全策略；ColorOS / MagicOS 的 ptrace 限制属平台限制。
- 镜像只做通路不做信任源（ADR-008）；Windows 客户机镜像不分发（N-VM-004 FR-002）。
- 归档能力不得复活为插件（SRS-004 FR-005）。
