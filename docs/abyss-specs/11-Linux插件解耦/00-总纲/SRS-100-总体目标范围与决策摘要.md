## 1. 目标与范围

| 编号 | 目标（可验证） |
| --- | --- |
| G-001 | 把 Linux 运行环境（rootfs / 镜像 / PRoot / QEMU / 会话 / 授权）整体收敛到单一独立 APK 插件 `abyss-plugin-linux`。 |
| G-002 | 应用构建器 `abyss-plugin-app-builder` 不再自带底座、不再拉起 PRoot、不再申请 Shizuku 授权，只保留预检、三路径编排、产物闭环。 |
| G-003 | 两插件间依赖显式声明、宿主可解析、可校验、可在不满足时 fail-closed 并给出人话引导。 |
| G-004 | 同一套 `RuntimeSession` 抽象覆盖 PRoot 用户态与 QEMU 完整系统，构建器代码不感知具体执行域。 |
| G-005 | 用户侧只安装 2 个 APK（宿主 + Linux 插件 + 构建器插件共 3 个），Shizuku 只授权 Linux 插件一次。 |
| G-006 | 大二进制资产（rootfs / VM 镜像）与小数据补丁（plugin.json / CHANGELOG）通道分离，互不阻塞。 |

**非目标**：不改写 Linux 内核、不提供 root、不绕过 SELinux；不把 Windows 镜像随插件分发；不实现桌面级构建性能；不改变主壳双仓库发布纪律；不复活任何已归档插件仓。

## 2. 现状锚点（克隆研究实测）

| 事实 | 证据 |
| --- | --- |
| 组织 19 个公开仓库：主仓 1、发布仓 1、插件中心 1、归档插件仓 13、引擎级插件仓 3 | GitHub API `orgs/abyss-tool/repos?per_page=100` |
| 应用构建器仅 15 个文件（manifest / 文档 / CI 脚本），`apk: null`，`patches: []`，v0.2–v0.6 全未勾选 | `abyss-plugin-app-builder/{README,ROADMAP,plugin.json,patches/index.json}` |
| 现有方案把 Alpine+PRoot 直接内嵌构建器，且构建器 `shizuku.ownAuth=true` | `abyss-plugin-app-builder/docs/ARCHITECTURE.md`、`plugin.json` |
| 虚拟机插件是独立 APK 骨架，也声明 `shizuku.ownAuth=true`，与构建器底座重复 | `abyss-plugin-virtual-machine/plugin.json`、`plugins.json` |
| `HUB-011` 明确「仅骨架，无实现代码」，`N-APP-002` 明确「规划中 · 待实现」 | 主仓 `docs/abyss-specs/04-插件生态`、`05-新增能力` |
| 全组织 0 个 `.so/.img/.apk/.zip/.tar` 二进制资产 | 全仓文件扫描 |

> 结论：**本次是架构前置设计**，在骨架落地前把形态定对，成本远低于先实现再拆分。

## 3. 功能需求

| 编号 | 需求描述（原子、可验证） |
| --- | --- |
| FR-001 | 新建 `abyss-plugin-linux`，形态为引擎级独立 APK，符合 `SRS-004` FR-001「自带完整引擎」准入门槛。 |
| FR-002 | Linux 插件对外只暴露 `linux-runtime-v1` 能力，不暴露 Shizuku Binder、不暴露 rootfs 绝对路径。 |
| FR-003 | 应用构建器 `plugin.json` 必须声明对 `abyss-plugin-linux` 的非可选依赖，并删除 `shizuku` 字段。 |
| FR-004 | 宿主必须在安装 / 启用 / 启动三处做依赖解析，任一不满足即拒绝并给出「请先安装/升级 Linux 插件」的人话错误。 |
| FR-005 | 任一插件不得绕过宿主直连另一插件的 exported service；能力绑定必须经 `PluginBroker` 签发令牌。 |
| FR-006 | Linux 插件必须同时实现 `PROOT_USERLAND` 与 `QEMU_VM` 两个执行域，且共享同一会话抽象。 |
| FR-007 | rootfs / 镜像资产必须走 `abyss-asset-v1`，禁止塞进 `abyss-patch-v1` 数据补丁包。 |
| FR-008 | 卸载 Linux 插件前，宿主必须提示依赖它的应用构建器将不可用，并给出级联处置选项。 |
| FR-009 | 全链路沿用既有纪律：SemVer、`UiState` 三态、SHA-256、备份→应用→失败回滚、纯 JVM 可测边界、fail-closed。 |
| FR-010 | 所有新增契约必须有版本化 schema、CI 校验脚本与测试夹具镜像（`src/test/resources`）。 |

> 纪律：每条 FR 至少被一条 AC 或一个自动化用例覆盖；追溯关系登记进 `QA-008 需求追溯矩阵`，由 spec-lint 校验。

## 4. 成功判据

| 编号 | 判据 | 度量方式 |
| --- | --- | --- |
| S-001 | 应用构建器仓内 0 个 PRoot / rootfs / QEMU / Shizuku 相关实现文件 | 仓库扫描 |
| S-002 | Linux 插件可在无构建器时独立启动一个 Alpine 会话并执行命令 | 端到端用例 E2E-01 |
| S-003 | 构建器在 Linux 插件缺失 / 版本过低 / 未授权三种情况下均给出可操作引导，不崩溃 | 用例 E2E-02~04 |
| S-004 | 三路径构建在 PRoot 域全部产出可安装 APK；QEMU 域至少跑通路径三 | ENG-100 §5 E2E 用例集 |
| S-005 | Shizuku 授权动作总数由 2 次降为 1 次 | 真机授权计数 |
| S-006 | `plugins.json` 中不存在已归档的虚拟机插件条目 | Hub CI |

## 5. 决策摘要

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| D-1 底座归属 | 独立 Linux 插件 | 底座是「完整引擎」，符合 ADR-001 插件化例外；复用方不止构建器（终端、脚本实验室、未来插件） |
| D-2 执行域 | 双域并存 | 用户要求「整个 Linux」；PRoot 轻快适合构建，QEMU 提供真正独立内核；两者共用一份资产与授权治理 |
| D-3 通信 | 宿主中介 + AIDL 受限代理 | 沿用 N-PLG-002 的同签名信任门，避免插件间互信黑洞 |
| D-4 ABI | HOST_API 升 v2 + 兼容期 | 依赖解析与能力绑定属宿主新职责，`minHost=2` 的插件在 v1 宿主 fail-closed |
| D-5 资产 | 新增 abyss-asset-v1 | ADR-011 已裁定数据补丁与二进制增量分离 |
| D-6 VM 仓 | 归档收编 | 避免两套镜像管线、两套 Shizuku 授权、两套前台服务 |

## 6. 失败语义与边界

- 坏数据 / 非法版本 / 路径穿越 / 签名不符 / 依赖缺失一律 fail-closed 拒绝并给人话错误，不猜测、不静默降级。
- 远端数据统一 `UiState`（Loading / Error / Data），加载中禁止展示假数据。
- Shizuku 不是 root（uid 2000）；不得暗示可绕过厂商安全策略；ColorOS / MagicOS 的 ptrace 限制属平台限制，必须明确告知。
