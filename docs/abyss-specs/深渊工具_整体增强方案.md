# 深渊工具 Abyss Tools · 整体增强方案

> 研究基线：`github.com/abyss-tool` 组织 19 个公开仓库全量克隆（2026-11-21）
> 版本基线：主仓 **v0.9.5 / versionCode 28**，发布仓 `version.json` 同步
> 配套交付：《规格说明书全集》**207 份**（`深渊工具_规格说明书全集.zip`）

---

## 一、结论先行

把 19 个仓库全部拉下来逐文件看完之后，判断很清晰：**这个项目的"框架与纪律"已经相当成熟，真正的缺口在"引擎落地"和"信任链最后一环"**。

- 主仓 `Abyss-Tools` 是一个 296 个文件、约 22 个 feature 模块的 Kotlin/Compose 多模块工程，更新引擎、插件框架、Shizuku 执行层、M3 + 液态玻璃、fail-closed 安全基线都已成型且有纯 JVM 单测覆盖；
- 发布仓、插件中心、CI 门禁、数据补丁格式构成了一条自洽的双仓库发布链，纪律文档（`AGENTS.md` / `ARCHITECTURE.md` / `SECURITY.md` / `UPDATE_CHANNEL.md`）写得比多数商业项目还认真；
- 但**三个"引擎级插件"全部只有骨架**：`abyss-plugin-app-builder` / `virus-guard` / `virtual-machine` 各 13–15 个文件，清一色是 `plugin.json`、`README.md`、`ROADMAP.md`、`CHANGELOG.md`、CI 与补丁脚本，**没有一行 Android/Kotlin 实现代码，没有 Gradle 工程，没有 APK**，`plugins.json` 里三个 `apk` 字段全是 `null`，路线图 v0.2–v0.6 全部未勾选；
- 与此同时，主仓 README 的 Phase 1b–4 四项未勾选、`ToolCatalog` 里 4 个 `FRAMEWORK` 占位、`patches.json` 长期为空数组、`SECURITY.md` 自己承认"清单尚未做 detached 签名"。

所以增强方案不是"再加几个功能"，而是**把已经画好的骨架填成可运行的引擎，同时把发布链最后一处信任单点补上**。下面给出五条主线、分期路线与验收口径；每一条都对应规格全集中的具体编号，可直接作为研发任务拆单。

## 四、差距分析（10 项，均带实测证据）

1. **三个引擎级插件零实现**。`plugins.json` 三个 `apk: null`，`patches/index.json` 的 `patches: []` 全是空链，ROADMAP 全部未勾选。插件生态目前是"目录页"而不是"能力"。
2. **插件 SDK 的 ABI 桥仍是预告**。`PLUGIN_SDK.md` 写明"AIDL 双向桥 / DexClassLoader 动态加载随 v0.2 发布流水线接入"，但 `PluginContract` 只定义了 `META_HOST_ENTRY` / `META_UI_ENTRIES` 常量，无消费方。
3. **Phase 1b–4 四项未动**：VT/ANSI 伪终端 + 本地 bootstrap、任务系统调用链 + DexClassLoader、沙箱 Hook + Python 完整引擎、Web 控制台 / 设备管理器 / 图标伪装。
4. **4 个 FRAMEWORK 占位长期无主**：`battery-doctor`、`code-editor`、`privacy-guard`、`time-shift`。
5. **二进制增量从未落地**。`patches.json` 为空，每次升级下载约 14MB 整包；`UPDATE_CHANNEL.md` 把 vcdiff 归为"另册"，至今无实现。
6. **清单无 detached 签名**。`SECURITY.md` 明确承认这是已知边界，当前防线只有"发布仓写权限最小化 + versionCode 单调 + APK 摘要校验"。叠加 v0.5.0 历史 jks 入库泄露，发布仓 PAT 是事实上的信任单点。
7. **发布说明质量滑坡**。v0.9.0 的 release-notes 有 5 条详实要点，而 v0.9.5 的 `notes` 只有 `"Merge PR #4: Fix security and functional bugs"` —— auto-release 直接把 PR 标题当发布要点。
8. **测试只有纯 JVM 单测**，无 `androidTest` / Compose UI 测试、无覆盖率门禁、无 lint/静态分析、无 SBOM/依赖审计。
9. **归档仓 manifest 漂移**：`abyss-plugin-app-manager`、`island`、`automation` 等仓的 `repo` 仍写 `Ultra-Guru/...`，与 `ChannelPolicy` 要求的 `^abyss-tool/abyss-plugin-...$` 不符。
10. **文档引用的"总体 SRS §6"并不存在**。README、多个插件仓 ROADMAP 都以其为里程碑依据，但组织内没有这份文档 —— 规格体系缺实体，跨仓契约靠人工记忆维持。

> 第 10 条正是本次交付 207 份 spec 的直接动因：把散落在 README / ARCHITECTURE / ROADMAP / release-notes 里的口径收敛成可追溯、可校验的单一事实源。

## 五、增强方案总纲（五条主线）

### 主线 A · 让三个引擎级插件真正跑起来（最高优先级）

这是投入产出比最高的一块，因为技术方案其实已经写完了（`app-builder/docs/ARCHITECTURE.md` 有 10KB 的完整设计），缺的只是实现。

| 插件 | 落地顺序 | 关键约束 | 对应规格 |
| --- | --- | --- | --- |
| 应用构建器 | 脚手架 → Alpine+PRoot 底座与 ptrace 探测降级链 → Shizuku 独立授权 → 路径一/二/三 → 三选一交互层 → 产物签名安装 → 补丁首链 | ColorOS/MagicOS 的 ptrace 限制无解只能降级；aapt2 的 glibc/musl/Bionic 错配要 `ldd` 验证；手机端 Gradle 10–30 分钟需资源约束 | `N-APP-001` … `N-APP-009` |
| 病毒拦截 | 安装事件拦截骨架 → 信任判定管线（纯 JVM）→ 误杀防护 → ClamAV 差量签名库 → VirusTotal 限额调度 → 全盘扫描处置 | 签名库全量约 300MB / 每日差量 1–2MB；免费额度 4 req/min、500 req/day；**默认只提示不静默卸载**；云查询只传哈希且默认关闭 | `N-VIR-001` … `N-VIR-006` |
| 虚拟机 | QEMU TCG 拉起 + 能力探测 → 镜像元数据/分卷/断点续传 → VNC 与输入路由 → 镜像市场 → 快照与性能档位 | ARM on ARM 优先；VNC 只绑 127.0.0.1；数 GB 镜像；Windows 镜像由用户自备，只提供运行时 | `N-VM-001` … `N-VM-005` |

**统一要求**：每个插件仓补齐独立 Gradle 工程 + 固定签名 CI，产物上 Release 后由 `sync_index.py` 自动把 `apk.sha256/sizeBytes` 填进 `plugins.json`；并各自发布首条 `abyss-patch-v1` 数据补丁，把宿主侧"下载 → 校验 → 备份 → 应用 → 回滚"闭环真正演练一遍。

### 主线 B · 补齐主壳深水区（Phase 1b–4）

按 README 已定的四个 Phase 推进，不另发明方向：

- **Phase 1b**：`N-TERM-001` VT/ANSI 渲染内核 → `N-TERM-002` 本地 PTY + bootstrap（解决交互式程序）；
- **Phase 2**：`N-BP-001` 蓝图变量/条件/子蓝图调用链、`N-BP-002` 触发器总线、`N-PLG-001` DexClassLoader、`N-PLG-002` AIDL 双向桥、`N-PLG-003` UI 入口发现；
- **Phase 3**：`N-PY-001` 自包含 Python 引擎、`N-SBX-001` 沙箱 Hook 层（让 26 款 `DeviceProfiles v2` 档案真正有消费方）；
- **Phase 4**：`N-WEB-001` Web 控制台（默认关闭 + 强制认证 + 仅局域网）、`N-DO-001` 设备管理器面板、`N-ICON-001` 图标伪装。

同时把 4 个 `FRAMEWORK` 占位转正（`N-BAT-001` / `N-CODE-001` / `N-PRV-001` / `N-TIME-001`），并补 `N-NET-001` VpnService 深度包审计、`N-MEDIA-001` FFmpeg 级转码两项能力缺口。**纪律**：每转正一项，必须同步 `ToolCatalog` 状态、`settings.gradle.kts` 模块、`AbyssRoot` 路由与 spec 状态，禁止"文档先打勾"。

### 主线 C · 信任链与发布链加固（M1 必做）

优先级最高，因为其余所有能力都建立在这条链可信的前提上：

1. `N-SEC-001` **三份清单 detached 签名**（Ed25519 / minisign）：`version.json` / `patches.json` / `plugins.json` 各带 `.minisig`，公钥内置客户端，客户端**先验签再解析**，失败即整页 Error，绝不"无签名也放行"；插件仓 `patches/index.json` 同样纳入。
2. `N-SEC-002` **RELEASE_TOKEN 最小权限**：fine-grained PAT 只授发布仓 Contents 写、90 天轮换、吊销演练脚本；三个插件仓各自独立 PAT。
3. `N-UPD-001` **vcdiff 二进制增量**：发布流水线生成差分包 → 客户端校验基 APK 摘要 → 合成 → **再次校验目标 APK 摘要** → 覆盖安装，失败自动回退整包。
4. `N-UPD-002` 灰度通道（复用已有 `channel` 字段）+ `N-UPD-003` 失败分类与本地诊断 + `N-EXP-003` 诊断中心。
5. `N-ENG-010` 发布说明质量门禁（≥3 条要点、breaking 首条显著标注、禁止 PR 标题直接当 notes）。
6. 轮换路径 `N-SEC-003` 作为预案保留，但**不在本轮执行**（签名变更会让存量用户全部卸载重装并打断补丁链）。

### 主线 D · 工程化与质量体系

- `N-ENG-001` 本地可复现构建（当前 README 明确"不做本地编译验证"，贡献者无法本地跑全门禁）；
- `N-ENG-002` 仪器化 / Compose UI 测试（首启引导门、返回栈旋转恢复、安装确认页转发、玻璃采样、组件固定）；
- `N-ENG-003` 覆盖率 + lint/detekt 门禁、`N-ENG-004` SBOM 与依赖审计、`N-ENG-005` 本地结构化指标（不外传）；
- `N-ENG-006` 国际化与无障碍、`N-ENG-007` 大屏/折叠屏、`N-ENG-009` 归档仓 `Ultra-Guru` 漂移治理；
- `N-ENG-008` **Spec 驱动流程**：PR 必须关联 spec 编号，新增 `spec-lint` 校验编号唯一、FR↔AC 覆盖、`ToolCatalog` ↔ `plugins.json` 一致性。

### 主线 E · 生态与体验补完

`N-EXP-001` 插件兼容性与推荐提示（minApp / Shizuku / 设备能力）、`N-EXP-002` 统一会话日志与撤销中心（把散在 AppMgr / SysPower / ShizukuKit 的历史收敛）、`N-EXP-004` 桌面快捷方式与白名单 Deep Link、`N-EXP-005` 备份包可选口令加密、`N-EXP-006` 插件权限透明化面板（独立 Shizuku 授权、云查询默认关闭等人话展示）。

## 七、关键约束与"诚实边界"

增强方案继承项目原有纪律，以下边界必须写进每一个新功能的 UI 与 spec：

- Shizuku 是 **uid 2000 的 shell 上下文，不是 root**，不能 `su`、不能任意突破 SELinux；ColorOS / MagicOS 对普通应用 `ptrace` 的限制只能靠降级链规避；
- 无 Root 不改 `ro.product.*`；App 读 `TelephonyManager` / `WifiManager` 仍是真值；状态栏覆盖层在锁屏与下拉快捷面板头部不显示；
- 内置终端当前是"单命令顺序执行、非交互式 PTY"，脚本实验室的 Python 依赖系统自带 CPython；在 Phase 1b/3 落地前不得宣称"完整终端 / 完整 Python"；
- 镜像只做通路不做信任源，一切资产强制 SHA-256；清单签名落地前，不得在文档中把 `version.json` 称作"可信"；
- 病毒拦截、云查询、Web 控制台一律**默认关闭 + 显式告知 + 最小外传**；处置默认只提示，白名单 + 人工确认双轨防误杀。
