## 1. 目标与范围

旗舰插件：Alpine + PRoot 底座 + 三路径构建。仓库实测 15 个文件，全部为 manifest / 文档 / CI 脚本，无 Gradle 工程、无 Kotlin 源码、无 APK；v0.2–v0.6 路线图全部未勾选，apk 字段为 null。

**目标**

- 把「框架预览」推进为可安装、可构建的真实插件 APK。
- 落地 v0.2 底座 → v0.6 交互层的完整链路。

## 2. 现状锚点（克隆研究实测）

- `abyss-plugin-app-builder/plugin.json`
- `abyss-plugin-app-builder/ROADMAP.md`
- `abyss-plugin-app-builder/docs/ARCHITECTURE.md`
- `abyss-plugin-app-builder/patches/index.json`

> 研究口径：2026-11-21 对 `github.com/abyss-tool` 组织下 19 个公开仓库（主仓 / 发布仓 / 插件中心 / 13 归档插件仓 / 3 引擎级插件仓）全量拉取，共 511 个文件；主仓 296 个文件、约 22 个 feature 模块。

## 3. 功能需求

| 编号 | 需求描述（原子、可验证） |
|---|---|
| FR-001 | 必须新增独立 Gradle Android 工程并接入 HOST_API v1 契约。 |
| FR-002 | 必须实现底座可用性探测与 Shizuku 降级链。 |
| FR-003 | 必须实现三条构建路径与失败切换。 |
| FR-004 | 必须建立固定签名的 APK 构建流水线并使 sync_index 自动填 apk。 |
| FR-005 | 必须发布首条数据补丁，打通插件补丁闭环。 |

> 纪律：每条 FR 必须至少被一条 AC 或一个自动化用例覆盖；下表 AC 为关键验收条件，完整覆盖关系由 `QA-008 需求追溯矩阵` 与 spec-lint 登记校验。需求变更需同步更新本文件与对应的测试夹具（`src/test/resources` 为通道契约镜像）。

## 4. 契约与接口

沿用宿主既有契约（`PluginContract.HOST_API_VERSION = 1`、`SemVer`、`UiState` 三态），本单元不新增跨模块接口。

## 5. 失败语义与边界

- Shizuku 不是 root（uid 2000），不提供越权能力；不得在文档中暗示可绕过系统安全策略。
- ColorOS / MagicOS 的 ptrace 限制无法靠代码优化解决，需明确告知不可用。

## 6. 验收标准

| 编号 | 验收条件 |
|---|---|
| AC-001 | CI 产出可安装 APK，plugins.json 的 apk.sha256 非空。 |
| AC-002 | 三路径各至少有一个端到端构建用例。 |

> 验收方法：纯 JVM 单测（`./gradlew test`）/ CI 门禁脚本 / 真机回归清单（Android 15 与 16 各一台）/ 通道清单校验，按单元性质择一或组合。

## 7. 依赖与风险

**依赖**

- `core:common`（SemVer / UiState / 渠道常量）

**风险**

- PRoot / aapt2 libc 依赖 / 手机端 Gradle 内存与耗时（10–30 分钟）等 6 项风险见 ROADMAP.md。
